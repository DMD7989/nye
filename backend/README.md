# N'yé — Backend

API REST Spring Boot pour la plateforme de signalement de personnes disparues N'yé.

## Stack

- Java 21, Spring Boot 4.1.1
- Spring Web, Spring Security (JWT), Spring Data JPA
- H2 (dev, en mémoire) / PostgreSQL (prod), schéma géré par Flyway dans les deux cas
- springdoc-openapi (Swagger UI)

## Lancer en local

```bash
./mvnw spring-boot:run
```

L'app démarre sur `http://localhost:8080` avec le profil `dev` par défaut (H2 en mémoire).
Deux comptes vérifiés sont créés automatiquement en dev :

- Admin — téléphone : `+22300000000` / mot de passe : `Admin1234!`
- Utilisateur démo — téléphone : `+22311111111` / mot de passe : `Demo1234!`

- Swagger UI : http://localhost:8080/swagger-ui.html
- Console H2 : http://localhost:8080/h2-console (JDBC URL : `jdbc:h2:mem:nyedb`, user `sa`, pas de mot de passe)

## Migrations de base de données (Flyway)

Le schéma n'est plus généré automatiquement par Hibernate (`ddl-auto=validate` partout, y compris
en dev) : il est entièrement défini par les scripts SQL versionnés dans
`src/main/resources/db/migration/` :

- `V1__create_users_table.sql`
- `V2__create_alerts_table.sql`
- `V3__add_moderation_to_alerts.sql`

Ces scripts sont écrits en SQL portable (types ANSI, `GENERATED BY DEFAULT AS IDENTITY`,
`TIMESTAMP WITH TIME ZONE`) pour s'exécuter à l'identique sur H2 (dev/tests) et PostgreSQL (prod) —
Flyway les applique automatiquement au démarrage, dans les deux environnements, et enregistre
l'historique dans la table `flyway_schema_history`.

**Ajouter une évolution de schéma** : créer un nouveau fichier `V3__description.sql` (numéro suivant,
jamais modifier un script déjà appliqué) dans `db/migration`, puis mettre à jour l'entité JPA
correspondante en cohérence. Comme Hibernate est en `validate`, tout décalage entre les migrations et
les entités fait échouer le démarrage immédiatement (et les tests, qui utilisent le même mécanisme).

## Endpoints principaux

### Auth (public)
- `POST /api/auth/register` — inscription (téléphone + mot de passe). Le compte est créé avec `phoneVerified: false` et un OTP est généré automatiquement.
- `POST /api/auth/login` — connexion, retourne un JWT
- `POST /api/auth/otp/request` — (ré)envoie un code OTP à un numéro (`{ "phone": "..." }`)
- `POST /api/auth/otp/verify` — valide le code (`{ "phone": "...", "code": "123456" }`) et marque le téléphone comme vérifié

En dev, aucune passerelle SMS n'est branchée : le code OTP est écrit dans les logs du serveur
(`[OTP] Code de vérification pour ... : XXXXXX`). À remplacer par un vrai fournisseur SMS avant la prod.

### Alertes
- `GET /api/alerts?lat=&lon=&radiusKm=` — alertes en attente + actives, triées par distance si `lat`/`lon` fournis (public)
- `GET /api/alerts/{id}` — détail d'une alerte (public)
- `GET /api/alerts/resolved` — historique des alertes clôturées (public)
- `POST /api/alerts` — publier une alerte (authentifié, **téléphone vérifié par OTP requis** — sinon 403)

**Visibilité avant validation (cahier des charges §13.1)** : tant qu'une alerte est `PENDING`, le
public (et les autres utilisateurs) ne voient qu'une version restreinte (`restricted: true`) —
position arrondie à ~1 km, photo masquée (`photoUrl: null`, `photoPending: true`), et nom réduit à
« Prénom N. » si `missingPersonIsMinor: true`. L'auteur de l'alerte et les administrateurs voient
toujours la version complète. Dès qu'un admin valide l'alerte (`ACTIVE`), tout le monde voit les
détails complets.

### Administration (rôle ADMIN requis)
- `GET /api/admin/alerts?status=PENDING|ACTIVE|RESOLVED|REJECTED` — tableau des alertes
- `PATCH /api/admin/alerts/{id}/validate` — valider une alerte en attente
- `PATCH /api/admin/alerts/{id}/close` — clôturer une alerte (avec note de résolution)
- `PATCH /api/admin/alerts/{id}/reject` — rejeter une alerte en attente (`{ "reason": "..." }`) — contenu frauduleux/sensible ou canular manifeste
- `GET /api/admin/users` — liste des utilisateurs
- `PATCH /api/admin/users/{id}/role?role=ADMIN|USER` — changer le rôle
- `PATCH /api/admin/users/{id}/suspend` / `/reactivate` — activer/désactiver un compte

### Dashboard analytique (rôle ADMIN requis) — Nyé-A3
- `GET /api/admin/dashboard/summary` — totaux par statut (dont `rejectedAlerts` et `flaggedPendingAlerts`), taux de clôture (résolues / alertes déjà validées), temps moyen de résolution en heures, nouvelles alertes sur 7 jours, statistiques utilisateurs (total, vérifiés, suspendus)
- `GET /api/admin/dashboard/trends?days=30` — série quotidienne (alertes créées / résolues par jour) sur la fenêtre demandée (1 à 365 jours), pour un graphique de tendance
- `GET /api/admin/dashboard/heatmap?status=ACTIVE|PENDING|RESOLVED` — points géolocalisés (précision exacte, vue admin) pour la carte de chaleur ; sans paramètre, retourne toutes les alertes

### Profil utilisateur (authentifié) — Nyé-F7
- `GET /api/users/me` — profil courant
- `PATCH /api/users/me` — modifier nom, email, langue
- `PUT /api/users/me/fcm-token` — enregistrer/rafraîchir le jeton de notification push de l'appareil
- `PUT /api/users/me/location` — mettre à jour la dernière position connue (appelé périodiquement par l'app, pas un suivi continu — voir §13.1)
- `PUT /api/users/me/notification-preferences` — activer/désactiver les notifications et régler le rayon (`radiusKm`, 10 km par défaut)

## Notifications push géolocalisées — Nyé-F5

Dès qu'un administrateur valide une alerte (`PATCH /api/admin/alerts/{id}/validate`), le backend
notifie automatiquement tous les utilisateurs qui :
- ont enregistré un jeton FCM (`PUT /api/users/me/fcm-token`) ;
- ont une position connue (`PUT /api/users/me/location`) ;
- ont les notifications activées (`notificationsEnabled`, activé par défaut) ;
- se trouvent à une distance ≤ leur `notificationRadiusKm` (10 km par défaut) de l'alerte ;
- ne sont pas l'auteur de l'alerte.

**En dev, aucun projet Firebase n'est configuré** : les notifications sont simulées et journalisées
(`[FCM] (simulé) Notification à <token> : ...`) au lieu d'être réellement envoyées — même principe
que le stub OTP. Pour activer l'envoi réel :

```bash
FCM_CREDENTIALS_PATH=/chemin/vers/service-account.json ./mvnw spring-boot:run
```

(fichier de clé de compte de service téléchargé depuis la console Firebase du projet).

Un échec d'envoi de notification n'invalide jamais la validation de l'alerte (erreur journalisée,
pas propagée).

## Modération de contenu — Nyé-A5

À la création d'une alerte, `ModerationService` filtre le nom de la personne disparue et la
description à la recherche d'expressions suspectes (demandes d'argent déguisées en avis de
recherche, liens à cliquer, etc. — voir la liste dans `ModerationService.SUSPICIOUS_PATTERNS`).
Une correspondance **ne bloque pas** la création : l'alerte est publiée normalement mais marquée
`moderationFlagged: true` avec un `moderationReason`, pour que les administrateurs la traitent en
priorité (`GET /api/admin/dashboard/summary` expose `flaggedPendingAlerts`).

**Vérification de la photo : stub non fonctionnel.** Sans service tiers branché, le contenu d'une
image ne peut pas être analysé — `moderatePhoto(...)` ne signale donc jamais rien. À remplacer par
un vrai fournisseur (AWS Rekognition, Google Vision SafeSearch, Azure Content Moderator...) avant la
mise en production, à l'image des stubs déjà en place pour l'OTP et FCM.

Un administrateur peut aussi **rejeter** une alerte en attente (`PATCH /api/admin/alerts/{id}/reject`),
qu'elle ait été signalée automatiquement ou non — canular manifeste, contenu frauduleux constaté
manuellement, etc. Une alerte `REJECTED` reste soumise aux mêmes règles de visibilité qu'une alerte
`PENDING` (§13.1/§13.2) : masquée du public et de la liste publique, mais son auteur garde accès au
détail complet, y compris le motif de rejet.

## Cycle de vie d'une alerte

`PENDING` (créée par un utilisateur) → `ACTIVE` (validée par un admin, visible publiquement/sur la carte) → `RESOLVED` (clôturée avec une note).
Une alerte `PENDING` peut aussi être **`REJECTED`** par un admin (contenu frauduleux/sensible ou canular) au lieu d'être validée.

## Tests

```bash
./mvnw test
```

43 tests, organisés en deux niveaux :

- **Unitaires** (Mockito, sans contexte Spring) — `GeoUtilsTest`, `OtpServiceTest`, `AlertServiceTest`,
  `AlertAnalyticsServiceTest`, `PushNotificationServiceTest`, `ModerationServiceTest`. Couvrent la
  logique la plus sensible : calcul/floutage de distance, expiration OTP, règles de visibilité
  restreinte/complète selon le statut et le rôle du visiteur (y compris `REJECTED`), calcul du taux de
  clôture et du temps moyen de résolution, filtrage des destinataires de notification par rayon et
  exclusion de l'auteur, détection des expressions suspectes indépendamment des accents/majuscules.
- **Intégration** (`@SpringBootTest` + MockMvc, H2 dédiée — voir `src/test/resources/application.properties`)
  — `AlertVisibilityIntegrationTest` : parcourt le cycle complet inscription → blocage sans OTP →
  vérification → publication → vue restreinte anonyme → vue complète pour l'auteur/admin → validation
  → vue complète publique, en passant par la vraie chaîne de sécurité (JWT + rôles) ; un second scénario
  couvre la modération automatique et le rejet par un admin. C'est ce niveau de test qui aurait détecté
  immédiatement le bug de configuration Spring Security rencontré pendant le développement (un
  `requestMatchers("GET", ...)` mal typé qui bloquait silencieusement les routes publiques).

La configuration de test (`src/test/resources/application.properties`) est indépendante du profil actif
sur la machine hôte, pour un comportement déterministe en CI comme en local. Le schéma y est également
géré par Flyway (`ddl-auto=validate`), donc les tests valident aussi la cohérence entités/migrations.
